# 開発ログのテンプレート

7 セクションの責務は排他的にし、別セクションの内容を繰り返さない。

| セクション | 書くこと                           | 書かないこと       |
| ---------- | ---------------------------------- | ------------------ |
| 概要       | タスク ID・タイトル・説明・関連 PR | 原因分析・実装詳細 |
| 分析       | 現象・原因、または背景・目標       | 実装手段           |
| 方針       | 機能要件・技術要件                 | 実装の手順         |
| 実装       | 領域別の変更内容                   | 要件・背景         |
| 検証       | 確認手順と結果                     | 実装内容の繰り返し |
| QA確認依頼 | 開発者の検証で担保できない観点     | 検証済みの内容     |
| 残課題     | 後続タスク・技術的負債・既知の制限 | 今回の対応内容     |

原因は「〜が機能していない」で止めず、コードか設計のレベルで書く。実装は PR 概要をコピーせず、diff から主要な変更を抜き出す。

出力時は全体をバッククォート 4 連のフェンス（言語指定 markdown）で囲み、本文中の 3 連フェンスと衝突させない。

<!-- prettier-ignore-start -->
````markdown
## 概要

**[タスクID] タスクタイトル**

- 対応内容の説明（1〜2 文）
- **関連PR**:
  - org/repo#XXXX

## 分析

**現象:**

- 具体的な問題点

**原因:**

- 技術的な原因（コード / 設計レベル）

<!-- 機能開発では「現象・原因」を「背景（なぜ必要か）・目標（実現したいこと）」に読み替える -->

## 方針

**機能要件:**

- 実現すべき機能

**技術要件:**

- 満たすべき技術的要件

## 実装

<!-- 存在する領域のみ（FE / BE / Infra / 共通） -->

### フロントエンド（org/repo#XXXX）

**1. 大項目**

- 具体的な変更（ファイル名・関数名を含める）
- 技術的判断の理由

### バックエンド（org/repo#XXXX）

**1. 大項目**

- 具体的な変更

## 検証

- 確認手順 → 結果
- CI / テストの状態

## QA確認依頼

<!-- 観点ごとに対象・環境・前提データ・期待結果を書く。なければ「なし」 -->

- **観点**: 対象 / 環境 / 前提データ / 期待結果

## 残課題

- 後続タスク・既知の制限・技術的負債（なければ「なし」）
````
<!-- prettier-ignore-end -->

## 記載量の目安

| セクション       | 項目数          | 各項目の長さ |
| ---------------- | --------------- | ------------ |
| 概要             | 1〜2 文         | 簡潔に       |
| 分析（現象）     | 3〜5            | 1 行         |
| 分析（原因）     | 2〜4            | 1〜2 行      |
| 方針（機能要件） | 3〜5            | 1 行         |
| 方針（技術要件） | 2〜3            | 1 行         |
| 実装（大項目）   | 領域ごとに 2〜4 | 2〜3 行      |
| 検証             | 2〜4            | 1 行         |
| QA確認依頼       | 0〜3            | 1〜2 行      |
| 残課題           | 1〜3            | 1 行         |

関連 PR は同一リポジトリ内でも `{org}/{repo}#{番号}`（例: `org/repo#123`）で書く。ベアの `#123` は転記先でリンクが切れる。
