# レビューレポートルール

`review-pr` / `review-blog` / `apply-review-feedback` が共通で使う、反証の手順と出力の型。何を P0 / P1 / P2 にするかと判定のラベルは、各 Skill（コードは `code-review-rule.md`）が決める。

## 反証

指摘の下書きを出したら、出力する前に 1 件ずつ崩しにいく。

1. 指摘が成り立たない理由を探す。コードなら呼び出し元のガード・型・テスト・設定、記事なら本文の別の箇所にある補足や前提
2. 崩れた指摘は捨てる
3. 根拠（`path:行`・本文の引用・公式 docs）で裏付けられた指摘だけを出す
4. 裏付けも反証もできなかった懸念は指摘に入れず、「反証できなかった点」に書く。何を確かめれば決着するかを添える

P0 / P1 があり、サブエージェントを使えるときは、その反証を別エージェントに任せる。渡すのは指摘と根拠の場所だけにする。自分の下書きを同じ文脈で崩すと甘くなるため。

## 判定

P0 / P1 が 1 件でもあれば ❌、P2 だけなら ⚠️、指摘が無ければ ✅ にする。

## 指摘の書き方

1 件の指摘は、そのままコメントとして貼れる形にする（PR ならインラインコメント、記事なら該当箇所へのコメント）。

- 「場所:」の行に、コードは差分上の `path:行`、記事は見出しと該当文の短い引用を書く
- コメントの 1 行目に `[P0]` / `[P1]` / `[P2]` のラベルを置き、空行を挟んでひとことコメントを 1 文書く。ひとことは「直し方」の要約を、レビュアーの前向きな感想として口語で書き（例: 「〜も一緒に書いておくともっと良くなりそう！」。です・ます調にしなくてよい）。問題を責める言い方ではなく、直すと良くなる方向で書く、見出しは「起きること」の要約を書く。依頼や命令の形（「〜してください」）にはしない。ひとことが見出しと同じ問題を述べているだけなら、直し方の感想に書き直す
- 見出しは太字 1 行で、原因ではなく利用者・読者から見える結果を書く
- 本文は次の 3 項目に分ける
  - **起きること**: どんな条件で、何が壊れるか・どう読まれるか
  - **理由**: そうなる原因と根拠
  - **直し方**: 推奨する修正。P0 / P1 で文だけでは伝わりにくいときは、コード例か Before / After の書き換え例を足す
- 本文はバッククォート 4 つの markdown コードブロックで囲む。中にバッククォート 3 つのコード例を入れられるようにするため

## 出力テンプレート

該当がないセクションは省く。「反証できなかった点」だけは常に出し、無ければ「なし」と書く。

`````markdown
### 判定: {✅ / ⚠️ / ❌ と Skill が決めたラベル}

{判定理由を 1〜2 文}

### 対象 / スコープ

{Skill 固有のサマリー（あれば）}

### 指摘

#### P0. 直さないと出せない

場所: `{path:行 / 見出しと該当文}`

````markdown
[P0]

{ひとことコメント}

**{見出し}**

- 起きること: {条件と結果}
- 理由: {原因と根拠}
- 直し方: {推奨する修正}

```{言語}
{コード例・書き換え例（任意）}
```
````

#### P1. 直したほうがいい

#### P2. 気になれば

### 良い点

### 反証できなかった点
`````
