# 図の規約

PR・ADR など、レビューや判断のために読む文書に図を添えるときの決まり。図は archify スキル（`~/.claude/skills/archify/SKILL.md`）で作る。図は本文の説明を補うもので、本文を図だけに置き換えない。

## 図を入れる場面

PR は、コードや設定の挙動を変えるなら図を 1 つ以上入れる。レビュアーが差分から変更の全体像を組み立て直さずに済むようにするためである。迷ったら入れる。次の PR には入れない。

- typo の修正、文言・コメントだけの変更
- 挙動が変わらないドキュメントだけの変更。Skill や規約のように、読んだ人やエージェントの作業が変わる文書は含めない
- 依存の更新、フォーマット・lint の修正だけの変更
- テストだけの変更
- 1 つの関数の中で閉じた修正で、呼び出し元から見た入出力も流れも変わらない

開発ログは PR と同じ基準で図を入れる。PR が無いときも、対応した変更をこの基準に当てはめる。

ADR などほかの文書は、次のどれかに当たるなら図を入れる。

- 処理の流れ、呼び出し順、状態、データ構造、責務の境界のどれかが変わる
- 変更が複数の PR やリポジトリにまたがり、マージ順や依存がある
- 設定や手順の変更で、人やツールが行う作業の流れが変わる

図を入れるときは次に従う。

- 図の直前に、その図で何を見てほしいかを 1 文で書く
- 1 つの図のノードは 15 個程度までにする。超えるなら観点ごとに図を分ける
- 変更の前後を比べる図は、下の「AsIs-ToBe 比較」に従う

## 図を置く位置

文書ごとに節の名前は違うが、図の役割で置く位置を決める。

- 全体像の図: 変更内容を書く節の先頭に置く
- 項目ごとの図: 該当する項目の下に置く
- 変更前（AsIs）を単独で示す図: 背景・原因を書く節に置き、変更後の図より先に読まれるようにする。変更内容の節には ToBe の図だけを置く。背景・原因の節が無いか、変更内容の節より後ろにある文書では、変更内容の節の ToBe の図より前に置く

| 文書     | 全体像                                                                       | 項目ごと                                 | 単独の AsIs                           |
| -------- | ---------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------- |
| PR       | `**変更点の概要**`                                                           | `### 主な実装内容` の該当タスクの下      | `**変更点の概要**` の ToBe の図より前 |
| 開発ログ | 「実装」の先頭（領域見出しの前）。1 領域だけの変更なら、その領域見出しの直後 | 「実装」の該当領域の、該当する大項目の下 | 「分析」の原因・背景                  |
| ADR      | 結論の先頭                                                                   | 決定内容の該当項目の下                   | 背景                                  |

プロジェクトの PR テンプレートで節の名前が違うときは、同じ役割の節に置く。社内のテンプレートでの節の名前は `~/.claude/skills/local-rules/references/conventions/diagram-rule.local.md` に書く（存在すれば Read し、矛盾時はそちらを優先する）。

## 図の種類

フローチャートに寄せず、示したいものに合わせて archify の type を選ぶ。

| 示したいもの                               | type           |
| ------------------------------------------ | -------------- |
| 処理の分岐・手順                           | `workflow`     |
| サービス・モジュール間の呼び出し順、非同期 | `sequence`     |
| データの流れと変換                         | `dataflow`     |
| ステータスと遷移の条件                     | `lifecycle`    |
| テーブルとリレーション                     | `erd`          |
| 型・クラスの継承や依存                     | `class`        |
| システム構成、レイヤーと責務の境界         | `architecture` |
| 段階的な移行・リリースの日程               | `timeline`     |

## 置き場所ごとの載せ方

archify の出力は単体の HTML である。置き場所によって載せるものを変える。

| 置き場所           | 載せるもの                                                     |
| ------------------ | -------------------------------------------------------------- |
| GitHub の PR       | HTML のビューアの Export メニューで書き出した PNG を本文に貼る |
| Notion（ADR など） | HTML を `/HTML` の HTML ブロックにアップロードして埋め込む     |

- PR の本文では、図を置く位置に PNG の相対パスで `![図の説明](./<PNG のパス>)` と書く。`gh pr create` か `gh pr edit` に `--body-file <本文> --attach <PNG のパス>` を付けると、PNG がアップロードされ、参照がアップロード先の URL に書き換わる（gh 2.105.0 で確認。相対パスは本文ファイルのディレクトリ基準）
- Notion の HTML ブロックは埋め込んだ後に中身を編集できない。図を直したら HTML を作り直してアップロードし直す
- 作った HTML はリポジトリにコミットしない。生成元の JSON も同じ

## AsIs-ToBe 比較

PR と開発ログの図は、変更後の姿だけでなく、何が変わったかが図から読めるようにする。

- `architecture` の変更前後は、AsIs と ToBe の JSON を 1 つずつ作り、`node ~/.claude/skills/archify/bin/archify.mjs compare architecture <AsIs.json> <ToBe.json> <出力.html>` で 1 枚の比較図にする。PR には比較図の Delta ビューを貼り、Notion には比較図の HTML をそのまま埋め込む
- ほかの type は 1 枚で比較できない。ToBe の図を 1 枚作り、追加・変更した接続や遷移に `variant: "emphasis"` を付ける。図の直前の 1 文で、強調した線が追加・変更箇所であることと、削除したものを書く
- 削除や置き換えが変更の中心で、ToBe だけでは伝わらないときは、AsIs と ToBe を別の図にして AsIs を先に置く
