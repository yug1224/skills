課題を読み取り、コードベースを調べて原因や現状を特定し、松竹梅の対応方針から実装プランを固める。調査と提案だけで、作業ツリーのファイルは変更しない（手順 5 の試作は一時的な worktree で行い、残さない）。

**Input**: チケット URL / ID、または課題の説明・エラーログ。無ければ入力を求めて終了する。

## Steps

1. 入力と前提を揃える
   - `~/.claude/skills/local-rules/references/overlays/analyze-issue.md` が存在すれば Read する（矛盾時はこちらを優先）
   - チケット URL / ID があるときは取得する（`~/.claude/skills/local-rules/references/conventions/ticket-retrieval-rule.local.md` が存在すれば Read してその手順に従う）
   - 対象リポジトリの `CLAUDE.md` / `AGENTS.md` の索引（無ければ `.claude/rules/`、それも無ければ `.cursor/rules/`）を確認し、課題に関係する規約だけ Read する
2. 調べる前に問題を捉え直す。記述が複数の問題に読めるなら、候補を 2〜3 個挙げ、それぞれにその問題を指す用語と、ほかの候補と見分ける兆候を書く。選んだ候補と理由を書く。記述に無いが、この分野の熟練者なら気にすることがあれば挙げる。候補が 1 つに絞れず、解釈の違いで調査対象が大きく変わるときだけ、手順 3 に進む前に候補を短く示してユーザーに確認する（1 つに定まるなら止めずに進む）
3. 原因を調べる前に挙動を確かめる
   - **不具合・既存挙動の修正**: 再現手順か失敗するテストを作り、実行して失敗を確かめる。テストは `~/.claude/skills/shared-rules/references/conventions/code-review-rule.md` の「一時ファイル」に従って書き、消す。実行したコマンドとテストコードは「再現 / 現行挙動」に残す（`/apply-plan` が失敗するテストとして使うため、手順 6 で「実装プラン」の「再現テスト / コマンド」へ引き継ぐ）。再現できなければ、試した手順と結果を「再現 / 現行挙動」に書いて先に進む
   - **機能追加・仕様変更**: 現行挙動を確認し、受け入れ条件を安くテストで書けるときだけ同様に失敗するテストを作って残す。書けないときは現行挙動と確認コマンドを「再現 / 現行挙動」に書く
4. コードベースを調査する。不具合は根本原因と直接原因を分けて特定し、機能追加・仕様変更は現行挙動と要件の差分・既存制約を整理する。意図が読めない既存コード・しきい値・回避策を変える必要があるときは、`~/.claude/skills/shared-rules/references/conventions/pstack-rule.md` に従って pstack の `why` で履歴と議論を確かめる（pstack が無く省略したときは「調査結果」に 1 行書く）
5. 対応方針を松竹梅で出し、「出力テンプレート（調査・方針）」の「課題サマリー」〜「推奨」を提示する。各案には、直った・満たしたと判断する完了条件と、それを示す証拠（通るテスト・実行結果）を書く。証拠のテストは、既存の seed・fixture で組めるかまで確かめる
   - **松**: 根本原因の解消と再発防止（機能追加では拡張性まで見据えた構成）
   - **竹**: 直接原因の修正（機能追加では既存パターンに沿った標準実装）
   - **梅**: 最小変更での解消
   - 複数の状態・中断・リトライ・並行操作が絡み、目視で抜け漏れを追い切れない課題、またはユーザー指定があるときは、`pstack-rule.md` に従って pstack の `statechart` で状態図と反例を出し、方針比較と手順 6 の質疑の材料にする（pstack が無く省略したときは「調査結果」に 1 行書く）。出した Mermaid 図・不変条件・反例パス・モデル外の前提は「調査結果」に含め、反例パスを「再現 / 現行挙動」に、不変条件と反例パスを各案と「実装プラン」の「完了条件 / 証拠」に引き継ぐ
   - 案どうしの違いを試作や計測で決められるなら、リポジトリ外（`/tmp/` 配下）に `git worktree add --detach` で一時的な worktree を作って試し、終わったら `git worktree remove --force` で消して、結果を「推奨」の根拠に書く。依存インストールが重く安く試せないときは試作を見送り、その理由を「推奨」に書く。作業ツリーのファイルは書き換えない。実験で決まらない好みや仕様の判断だけを手順 6 の質疑に回す
6. `~/.claude/skills/grilling/SKILL.md` を Read して質疑で詰め、「出力テンプレート（実装プラン）」を埋めて提示する。手順 5 の提示と同じターンで最初の質問（採用案の確認など）を続けてよい。続く回で元に戻しにくい決定（仕様、外部 I/F、API・DB スキーマ、責務を置く層）と完了条件を問う。内部の型や関数シグネチャの細部は `/apply-plan` に委ねる。選択肢だけで答えられる回は質問ツール（`AskQuestion` / `AskUserQuestion`）、比較や自由記述を含む回は `grilling` の書式に揃える（1 ターンに混在させない）。問う前に、その決定を作るのに要るデータの読み先と使える既存の仕組みを調べ、作れることを確かめる（答えをもらってから調べて問い直さない）。ユーザーには決定だけを問う。ユーザーが「質疑なし」と言ったら推奨案で埋める

## 出力テンプレート（調査・方針）

原因や現状を特定できなかったときは、調べた範囲と推測を書いたうえで「追加調査の方向性」を足す。

```markdown
## 課題サマリー

{課題内容を 1〜2 文}

## 問題の捉え方

- **候補**: {問題の候補 / 用語 / 見分ける兆候}（1 つに定まるなら「1 つ」と書く）
- **採用**: {選んだ候補と理由}
- **見落としやすい点**: {記述に無いが気にすべきこと}

## 再現 / 現行挙動

- **手順**: {実行したテストかコマンド}
- **期待値**:
- **実際の結果**:

## 調査結果

- **根本原因**（機能追加では **現行挙動**）:
- **直接原因**（機能追加では **要件との差分・制約**）:
- **関連コード**: `path:行` と該当箇所の引用

## 影響範囲

- {影響を受けるモジュール・機能}

## 対応方針（松竹梅）

### 松

- **内容**:
- **変更対象**:
- **完了条件 / 証拠**:
- **リスク**:
- **想定工数**:

### 竹

（松と同じ項目）

### 梅

（松と同じ項目）

## 推奨

{推奨する方針と理由}
```

## 出力テンプレート（実装プラン）

手順 6 の質疑完了後に提示する。別セッションの `/apply-plan` にそのまま渡せるよう、この節だけで完結させる。

```markdown
## 実装プラン

- **課題 / チケット**: {課題の要約。チケット URL / ID があれば併記}
- **採用案**: {松 / 竹 / 梅 と方針・変更内容の要約}
- **決定事項**: {質疑で決めたこと（仕様・外部 I/F・DB スキーマ・責務を置く層）}
- **変更対象**: `path`
- **参照した規約・既存実装**: `path`（該当が無ければ「なし」）
- **再現テスト / コマンド**: {手順 3 で確認したコマンドやテストコード、反例パス。無ければ「なし」}
- **完了条件 / 証拠**: {検証コマンド・テスト、`statechart` の不変条件と反例パス}
- **範囲外 / 共有**: {別チケットに回すことと、仕様の変更を共有・合意する相手}
```
