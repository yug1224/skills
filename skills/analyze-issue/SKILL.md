チケットの課題を読み取り、コードベースを調べて原因を特定し、松竹梅の対応方針から実装プランを固める。調査と提案だけで、コードは変更しない（手順 5 の試作は一時的な worktree で行い、残さない）。

**Input**: チケット URL または ID（必須）。

## Steps

1. チケットを取得する（`~/.claude/skills/local-rules/references/conventions/ticket-retrieval-rule.local.md` が存在すれば Read してその手順に従う）
2. 調べる前に問題を捉え直す。チケットの記述が複数の問題に読めるなら、候補を 2〜3 個挙げ、それぞれにその問題を指す用語と、ほかの候補と見分ける兆候を書く。選んだ候補と理由を書く。チケットに無いが、この分野の熟練者なら気にすることがあれば挙げる
3. 原因を調べる前に、再現手順か失敗するテストを作り、実行して失敗を確かめる。テストは一時ファイルに書き、終わったら消して、コマンドとテストコードを「再現」に残す（`/apply-plan` が失敗するテストとして使う）。再現できなければ、試した手順と結果を「再現」に書いて先に進む
4. 原因を調べ、根本原因と直接原因を分けて特定する
5. 対応方針を松竹梅で出し、「出力テンプレート」で提示する。各案には、直ったと判断する完了条件と、それを示す証拠（通るテスト・実行結果）を書く。証拠のテストは、既存の seed・fixture で組めるかまで確かめる
   - **松**: 根本原因の解消と再発防止
   - **竹**: 直接原因の修正
   - **梅**: 最小変更での解消
   - 案どうしの違いを試作や計測で決められるなら、`git worktree add --detach` で作った一時的な worktree で試し、終わったら `git worktree remove` で消して、結果を「推奨」の根拠に書く。作業ツリーのファイルは書き換えない。実験で決まらない好みや仕様の判断だけを手順 6 の質疑に回す
   - 提示する前に `~/.claude/skills/yomiyasu/SKILL.md` を Read して推敲する（存在するときだけ）。推敲後も出力テンプレートの書式を優先する
6. `~/.claude/skills/grilling/SKILL.md` を Read して質疑で詰め、「実装プラン」を埋める。最初の回に採用案を、続く回で元に戻しにくい決定（データの形、API・DB スキーマ、モジュールの境界）と完了条件を問う。問う前に、その決定を作るのに要るデータの読み先と使える既存の仕組みを調べ、作れることを確かめる（答えをもらってから調べて問い直さない）。ユーザーには決定だけを問う。ユーザーが「質疑なし」と言ったら推奨案で埋める。埋めた実装プランも手順 5 と同じく推敲してから提示する

- **見落としやすい点**: {チケットに無いが気にすべきこと}

- **実際の結果**:
