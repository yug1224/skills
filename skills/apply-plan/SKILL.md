実装プランを設計・実装し、セルフレビューまで進める。コミット・push・PR はしない。

**Input**: `/analyze-issue` の「実装プラン」（会話中）か、プランを書いたファイル・チケット。無ければ入力を求めて終了する。

## Steps

1. `~/.claude/skills/shared-rules/references/conventions/pstack-rule.md` と `code-review-rule.md` を Read する。`~/.claude/skills/local-rules/references/conventions/` の `coding-rule.local.md` と `agent-run-rule.local.md` は存在するものだけ Read する（作業範囲・ループ・終了報告は `agent-run-rule.local.md` を優先）
2. 設計する。新しい型・シグネチャ・モジュールの境界を作る変更や、状態の持ち主が変わる変更は、pstack の `architect` で形を決める。それ以外は扱うデータの形だけ決める。どちらでも、足す関数と同じ変換・判定をする既存の関数を探し、あれば使う。決めた形がプランの決定事項と食い違ったら、実装せずにユーザーに問う
3. 実装する。プランの「再現」に安く書けるテストがあれば、先に書いて失敗を確かめてから直す
4. プランの完了条件の証拠（テスト・コマンドの実行結果）を取る
5. 変更範囲に pstack の `no-comments` を通す
6. 実装の経緯を渡さないサブエージェントに、`/review-pr` の手順でローカル差分をレビューさせる。渡すのは比較先とプランだけにする（自分で読み直すと自分の設計に引っ張られる）。P0/P1/P2 が 0 件になるまで直して、新しいサブエージェントで再レビューする。上限は 3 周で、残ったら止めて残件にする。前の周より P0/P1/P2 の件数が減らなければ、上限の前でも止めて残件にする。P2 を見送るのは、直すとプランの範囲を超えるときだけにし、理由を書く
7. 終了報告を出す

## 終了報告

```markdown
## 実装サマリー

{プランの採用案と、実際に変えたこと}

## 完了条件 / 証拠

- {完了条件}: {実行したテストかコマンドと結果}

## セルフレビュー

- **周回**: {n} 周
- **残った指摘**: {P0/P1/P2 の残件。無ければ「なし」}
- **見送った P2**: {指摘と理由}

## 省略した手順

- {pstack が無いなどで飛ばした手順と理由}

## 残件

- {ユーザー待ちの作業（コミット、push、PR など）}
```
